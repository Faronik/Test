# КАТЕКС — учёт инструмента, C++ / PostgreSQL

Сервер работает на **C++20**, база данных — **PostgreSQL 17**. Интерфейс обращается к документированному REST API. Для запуска через Docker Compose Python, Node.js, компилятор C++ и отдельно установленный PostgreSQL **не нужны**: приложение и база запускаются в контейнерах.

## Запуск на Windows

1. Установите и запустите Docker Desktop с Linux-контейнерами (WSL2).
2. Распакуйте проект, запустите `start.bat`.
3. Дождитесь сборки. Откройте `http://localhost:8000` и создайте администратора.

На Linux-сервере установите Docker Engine и Docker Compose, затем выполните:

```sh
./start.sh
```

Скрипт создаёт `.env` со случайным паролем PostgreSQL, если файла ещё нет. Первый запуск скачивает базовые образы и пакеты, собирает C++-сервер; для него нужен интернет. Последующие запуски используют собранный образ. Не удаляйте `.env`: он нужен для повторного подключения к вашей базе.

Для других компьютеров локальной сети используйте адрес сервера и порт 8000. `TOOLSTOCK_BIND=0.0.0.0` открывает порт на сетевых интерфейсах; можно указать `127.0.0.1` для работы только локально. Первого администратора создайте до предоставления общего доступа. Для внешнего доступа поставьте HTTPS reverse proxy и задайте `TOOLSTOCK_SECURE_COOKIE=1`.

Проверить состояние и журналы:

```sh
docker compose ps
docker compose logs app db
docker compose stop
docker compose start
```

При обновлении исходников: `docker compose up -d --build`. Данные находятся в отдельных томах `postgres_data` и `photos`. Команда `docker compose down -v` удаляет эти тома — не используйте её для обычного обновления.

## Перенос из Python / SQLite

Не заменяйте старую папку `data` пустыми данными. Сначала остановите Python-сервер и сохраните копию всей папки `data`, включая фотографии. Новую C++-версию разверните отдельно, не создавая в ней администратора: импорт должен выполняться в пустую PostgreSQL-базу.

```sh
docker compose up -d db
docker compose build app
docker compose run --rm --no-deps -v "/ABSOLUTE/PATH/TO/OLD/data:/legacy:ro" app \
  toolstock --import-sqlite /legacy/toolstock.sqlite3 /legacy/photos
docker compose up -d app
```

На Windows путь привязки может выглядеть как `C:/warehouse/data:/legacy:ro`; команду можно выполнить одной строкой. На Linux файлы копии должны быть доступны для чтения контейнеру. Импортёр написан на C++ и встроен в серверный бинарный файл; Python не требуется.

Переносятся карточки, характеристики, фото, учётные записи с совместимыми хешами паролей, пользовательские роли/права, станки, рабочие, закрепления, движения, история исправлений и закупочные заявки со статусами. Идентификаторы сохраняются; новые последовательности PostgreSQL продолжаются после последнего перенесённого ID. После переноса войдите заново: сеансы и старые ключи повторной отправки не копируются.

Импорт не изменяет исходную SQLite-базу. Он проверяет её целостность, число записей, фотографии и отрицательные остатки; ошибка откатывает вставки. В непустую целевую базу импорт запрещён. Старые дробные количества, повреждённые ссылки и отсутствующие фото требуют сверки, а не автоматического округления или пропуска. Поддерживается структура последней Python-версии этого проекта; для значительно более старых версий сначала обновите копию базы через прежнюю версию.

## API

- Интерактивная документация: `http://SERVER:8000/api/docs`.
- OpenAPI 3.0: `/api/openapi.json`.
- Контракт: [docs/API.md](docs/API.md).
- Healthcheck: `/health`.

«Открытый API» означает документированный интерфейс для интеграций. Запись и производственные данные защищены авторизацией и ролями. Внешние клиенты получают Bearer token через `/api/v1/auth/login`; браузер использует HttpOnly cookie и CSRF. Повтор изменений защищён `Idempotency-Key`.

## Возможности

Каталог инструмента и оснастки, отраслевые параметры и ISO-пластины, фото, поиск и группировка; поступление, выдача на рабочего и станок, частичная сдача, списание; очередь и приёмка после переточки с отдельной карточкой; связанные исправления и отмены за 24 часа; остатки, отчёты, CSV; закупочные заявки, завершение, архив и восстановление; системные и пользовательские роли, станки/рабочие и учётные записи. Длинные справочники ограничены по высоте и поддерживают поиск. На мобильном экране остаток и ячейка показаны в карточке.

Интерфейс теперь является клиентом API, а не страницами, формируемыми Python. Адреса разделов используют `#catalog`, `#operations`, `#admin`. API v1 — новый контракт; старые URL форм Python больше не обслуживаются. Предыдущая рабочая версия сохранена в истории Git (commit `bf94f36`).

## Сборка без Docker

Нужны C++20, CMake 3.20+, pkg-config, PostgreSQL client development libraries, OpenSSL, cpp-httplib, nlohmann-json и SQLite3 (только для импортёра). Пример для Debian 12:

```sh
apt-get install g++ cmake make pkg-config libpq-dev libssl-dev libsqlite3-dev libcpp-httplib-dev nlohmann-json3-dev
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 2
# Укажите DATABASE_URL либо PGHOST, PGPORT, PGDATABASE, PGUSER, PGPASSWORD.
./build/toolstock
```

Нативный бинарный файл запускайте из корня проекта либо задайте `TOOLSTOCK_WEB`, `TOOLSTOCK_SQL`, `TOOLSTOCK_DOCS`, `TOOLSTOCK_DATA`. Для внешнего PostgreSQL используйте поддерживаемые libpq параметры TLS, включая `sslmode=verify-full` и доверенный корневой сертификат.

## Резервная копия

На Linux `./scripts/backup.sh` останавливает только приложение на время согласованного копирования, сохраняет PostgreSQL dump и фотографии и запускает приложение обратно. Результат — `.backups/TIMESTAMP/database.dump` и `photos.tar`; перенесите копию на другую машину.

Восстановление выполняйте в отдельное развёртывание: остановите приложение, восстановите dump через `pg_restore` в PostgreSQL и фотографии в том `photos`, затем запустите сервер. Перед заменой рабочих данных проверьте восстановленную копию.

## Проверки разработки

Для API-тестов нужен Node.js 18+ только на машине разработчика. Тесты требуют отдельного свежего экземпляра без администратора и отказываются работать с заполненной базой:

```sh
TOOLSTOCK_TEST_URL=http://127.0.0.1:8000 node tests/api.mjs
```

Браузерные тесты используют Playwright и не входят в зависимости серверного контейнера. Сведения о фактически выполненных проверках — [VALIDATION.md](VALIDATION.md).

Дополнительные проверки для разработчика после API-тестов:

```sh
node tests/domain.mjs
# Node.js 24+, отдельный тестовый Compose-проект:
TOOLSTOCK_TEST_PROJECT=toolstock-cpp node tests/migration.mjs
# Python + Playwright только на машине разработчика, не в сервере:
python tests/browser_cpp.py
```
